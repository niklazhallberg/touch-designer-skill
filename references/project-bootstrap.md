# Project bootstrap — central skill ↔ per-project setup

How a new TouchDesigner project consumes this central skill, what Embody generates per project, and the verified working configuration.

---

## What lives where

| Central skill (`~/.claude/skills/touch-designer-skill/`) | Per TD project (auto-generated by Embody) |
|---|---|
| `SKILL.md` (front door, loaded by Claude Code on TD context detection) | `<project>.toe` (your work) |
| `skills/*/SKILL.md` × 7 (canonical workflow snapshots) | `.mcp.json` (Embody auto-creates at TD startup) |
| `rules/*.md` × 4 (canonical operational rules) | `.embody/envoy-bridge.py`, `.embody/envoy.json`, `.embody/project.json` |
| `references/*.md` (growth-protocol, gotchas, patterns, components) | `CLAUDE.md`, `AGENTS.md` (Embody generates from Aiclient toggle) |
| `CHANGELOG.md` (biography of learnings) | `.claude/skills/`, `.claude/rules/` (Embody regenerates) |
| `scripts/td-new`, `scripts/session-sync.sh` | `.claude/settings.local.json` (per-machine perms allowlist) |
| `templates/td-project/` (the scaffold copied by `td-new`) | `.venv/`, `Backup/`, `TDImportCache/`, `logs/` (TD runtime, gitignored) |

**Path A (sidecar) is the chosen integration model.** Embody continues to auto-regenerate project-local `.claude/skills/` and `.claude/rules/`. The central repo holds canonical snapshots + everything Embody doesn't manage (`references/`, `CHANGELOG`, growth-protocol, sync hook, scaffolder). No symlinking; no disabling of Embody regen.

## End-to-end flow for a new project

**One-time per machine** (~3 minutes manual):

```bash
# 1. Clone the skill to its canonical location
git clone <your-fork-url> ~/.claude/skills/touch-designer-skill

# 2. Wire the SessionStart sync hook in ~/.claude/settings.json
# Add this entry to "hooks.SessionStart[].hooks":
#   {"type": "command",
#    "command": "~/.claude/skills/touch-designer-skill/scripts/session-sync.sh"}
# (See scripts/session-sync.sh header for the full snippet.)
```

**Per new TD project** (~30 seconds + a TD handful of clicks):

```bash
cd ~/Projects/
~/.claude/skills/touch-designer-skill/scripts/td-new my-new-project
cd my-new-project
```

Then in TouchDesigner:

1. **File → Save As… → `my-new-project.toe`** (save in the scaffolded folder)
2. **Drag the latest `Embody.tox`** (from [github.com/dylanroscover/Embody/releases](https://github.com/dylanroscover/Embody/releases)) into `/project1`
3. On the Embody COMP, set:
   - **AI Client** = `Claude Code`
   - **AI Project Root** = `Git root` (or your repo root if monorepo)
   - **Envoy Enable** = `On`
4. **Save (⌘S).** Embody generates `CLAUDE.md`, `AGENTS.md`, `.claude/skills/`, `.claude/rules/`, and `.mcp.json` automatically.
5. `cd <project> && claude` — the SessionStart hook syncs the central skill; the project's own Embody-generated CLAUDE.md becomes the front-door context.

## Conflict resolution when central ↔ project-local diverge

This will happen eventually: Embody's auto-regen may produce a slightly different version of a skill or rule than the central canonical snapshot. The rule:

| Conflict type | Winner |
|---|---|
| Project-local Embody-generated is fresher (Embody version newer) | Use project-local; backport useful changes to central repo |
| Central repo has an addition not yet in Embody (e.g., new reference, new rule) | Use central; project-local will catch up at next Embody regen |
| Both have edits to the same workflow | Surface conflict to user; pick deliberately |

**Don't silently merge** — the growth-protocol's discovery commits should be added to the central repo only, then propagated to projects as Embody regenerates. If you hand-edit a project-local skill, that edit is ephemeral; copy it to central before it's overwritten.

## When team-share lands (future)

The structure above is single-user but team-ready. To scale to a team:

1. Push the central repo to a shared private remote (Valtech org, GitHub team, etc.).
2. Each colleague clones to `~/.claude/skills/touch-designer-skill` and wires the SessionStart hook.
3. Add `bin/install.sh` (port from LS skill) to automate the clone + hook setup for non-technical colleagues.
4. Add branch protection on `main`; switch the discovery commit flow from direct push to PR.
5. Add a `CONTRIBUTING.md` describing the in-flow ask protocol from the discoverer's perspective.

The references and growth-protocol are already written in plain English, project-agnostic — no rewrite needed. Only the installation surface needs the team-grade additions.
